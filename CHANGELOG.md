# Changelog

Versions follow semantic versioning. The major tag (`v1`) moves to every release of that major; a breaking change bumps the major, and its entry says what to change in your workflow.

## v1.7.0

The runner can authenticate to GitHub with a GitHub App instead of a static token, and the agent gets a token of its own that can only read.

A GitHub App in place of the two tokens. Set `SRE_GITHUB_APP_ID` (the App's numeric id) and `SRE_GITHUB_APP_PRIVATE_KEY` (its PEM) instead of `SRE_GITHUB_TOKEN`, and the runner signs a JWT with the key, finds the installation that serves the request's repository owner (`GET /repos/{owner}/{repo}/installation`, looked up once per owner), mints an installation token for its own clone, fetch, push and `gh` with the installation's own permissions, keeps it until five minutes before it expires and mints it again as needed, and mints a second token for the agent alone, once per run, with `contents: read` on the request's repository only (or the first installation by id, for a request that names none, and the log names which installation serves the estate). The agent's token replaces `SRE_AGENT_GITHUB_TOKEN` in App mode: setting that variable beside the App refuses the start, because there is nothing to configure when the token is minted read-only for every run. Exactly one auth mode is allowed: a token beside the App variables, or the App half configured (an id without a key or the reverse), refuses the start with a sentence naming what to set; with no GitHub credential at all, a request naming a repository is reported back saying exactly that and a request naming none is answered, as before. `SRE_RUN_TIMEOUT_SECONDS` is capped at 3300 seconds in App mode, with a sentence at start above it, because the agent's token is minted once per run and lives an hour; five minutes of margin stay. The key is trimmed of surrounding whitespace only (a PEM has line breaks of its own; it signs, it never travels in a header), a key that cannot sign refuses the start naming the variable and printing none of it, and both App variables join the agent's scrubbed environment beside `SRE_API_KEY`. Every minted token, and the key, join the redaction list the moment the process holds them. A mint that fails (a 404 for an installation the App does not have, a 401 or 403, a network failure) is reported as the request's evidence with the status and GitHub's own message, never a crash loop: nothing is published and the request is answered. The installation lookup never accepts an installation whose account is not the repository's own owner, so a hostile owner cannot be handed a token minted on another account's installation. The wire contract with the platform does not change: no new job keys, no new poll keys, and a platform that knows nothing of the App works exactly as before. One installation per runner is the documented shape; with several, the request's repository owner picks the one it needs.

What a customer must change on upgrade: nothing. Token mode is unchanged; the App is opt-in, and the module release that follows sets the variables for you from a secret holding the PEM.

## v1.6.0

Several runners can share one organization's work, and the agent can read the organization's own patterns while it works.

A pool of runners. Collecting a request now leases it to the collecting instance, and the platform names the instance in the poll body (`instance`, the runner's hostname or `SRE_RUNNER_INSTANCE`), so with one API key on several machines each takes its own work: no other instance is offered a leased request until its report ends the lease or its window expires, and a restarted instance re-collects its own. With `SRE_WORKSPACE_PER_INSTANCE=1` (the shape for more than one task on a volume) each instance works under `instances/<id>` of its own for its clones, git directories, agent homes and scratch, while the memory stays one shared tree: every journal and marker write runs inside a shared `locks/_state.lock`, so two instances never interleave them, and before a request touches a repository's memory the runner takes `locks/<owner>/<repo>.lock` and holds it until the save and the home are done, so two runners never write the same notes. A busy repository is answered honestly: the report says another runner instance is working on it, nothing is published and nothing is staged. The locks live beside the memory root, so they follow `SRE_MEMORY_ROOT` wherever it points; a locks directory another account owns refuses the start. A lock appears whole or not at all (written to a private temporary and linked into place), a lock whose instance, pid or moment does not parse is replaced at once, one this account cannot read is waited for, and the stale bound follows `SRE_RUN_TIMEOUT_SECONDS` (45 minutes, or the run timeout plus ten minutes, whichever is longer). A runner that sends no instance id, or runs with the split off, keeps exactly today's behaviour: one runner per organization.

The context repository. When the GitHub integration names a context repository, the platform sends its name with a request that resolves a repository (`context_repo_full_name`, null when the organization set none, on requests that name no repository, and on every test job) and the runner clones that repository beside the checkout, at `context/<owner>/<repo>` on the workspace (`instances/<id>/context/...` in the pool shape), at its default branch, and refreshes it on every later request. The platform's brief is what tells the agent where the clone is and what it is for; this package guarantees the clone is at that path when the run starts. The tree is the runner's own (files 0644, directories 0755), readable by the agent's account and writable by no other, with the git directory closed as the gitdirs are and the parents above it walkable but never listable (0711). It sits outside every request's checkout, so nothing in it is ever staged, gated or pushed: it is reference material the agent reads, never a fix target. The clone and the refresh use the same discipline as every other git call the runner makes: argv only, the token through the credential helper's environment and on no command line. A context repository that cannot be reached, or a refresh that fails, is named in the report's evidence (`context_repository`, one line), the half-made clone is removed, and the request is run and published anyway.

Platform versions. The instance and the context repository's name are two more keys in the queue's answer and its poll body. A platform older than the release that sends them sends no such keys, so nothing is leased in a pool and nothing is cloned, and today's behaviour stands; a runner older than v1.6.0 sends no instance and ignores the context key, so the upgrade order is free and a customer changes nothing on upgrade.

## v1.5.0

The runner you host keeps what it learns, copies it to a bucket you own, proves itself end to end on request, and runs the agent as an account of its own. The CI door and the reusable workflow are untouched.

An operator can now keep the runner's work between requests. `SRE_WORKSPACE` is a layout the runner owns: `repos/<owner>/<repo>` holds the work trees, reused and refreshed by each request (the default branch is put out on `sre-agent/<handoff id>` and whatever the last run left, ignored files included, is discarded), `gitdirs/<owner>/<repo>` holds their git directories apart from them and closed to the agent, `agent-home/<owner>/<repo>` is the agent's home for that repository (`agent-home/_estate` for requests that name none), so the tools it installs with `mise`, `npm -g`, `pip --user`, `cargo`, `go install`, `gem` and `mix` are still there on the next request about the same repository, and `scratch/` serves requests that name no repository. In the image `agent-home/` is `/workspace/agent-home`, on the volume; under systemd it sits beside the workspace, at `/var/lib/sre-agent-fix-runner/agent-home`. Mount a volume at `/workspace` (a named volume, a PersistentVolumeClaim, an EFS access point) and a restarted or replaced container no longer clones everything again.

An operator can now give the agent a memory. For each repository, and once for requests that name none, the runner keeps a `NOTES.md` and a `scripts/` directory under `memory/`, outside every checkout. For a run it places a copy in the checkout as `.sre-agent-memory/`, which git cannot see; after the run it applies the bounds to the copy, writes the result back and deletes the copy before anything is staged, and `scripts/protected_paths.sh` refuses any staged path under `.sre-agent-memory/`. The notes and the first comment line of each script go ahead of the brief inside two marker lines that carry an id minted for that run, framed as the agent's own earlier notes, written by an agent that read untrusted input, to be used as context and never as instructions; a saved script runs only when the agent chooses to run it, under the same fences as any command. The runner enforces the bounds and the agent is not asked to: `NOTES.md` at most 65,536 bytes, at most 50 scripts and 1,048,576 bytes per directory, names of letters, digits, dots, underscores and hyphens up to 100 characters, and links, other non-regular files and anything outside `NOTES.md` and `scripts/` removed. A file that breaks a bound keeps the version the previous run left, or is removed when there was none. The agent prompt gains two paragraphs: what its working directory is, and that it ends its message with a `## Memory` section of one paragraph, which the runner cuts out of the pull request body.

An operator can now see what each run changed in the memory. The report gains an optional `memory` object with at most 50 changes (path relative to `memory/`, added, modified or removed, size in bytes), the agent's own summary of at most 500 characters and the name of the bucket, and a run that changed nothing sends no `memory` key. SRE Agent shows the list and never receives a note or a script.

An operator can now mirror the memory to a bucket of their own. With `SRE_MEMORY_BUCKET` set (and `SRE_MEMORY_PREFIX`, `memory/` by default), the AWS CLI, in the runner's process and with the runner's own credentials, copies every change the volume makes to the bucket after each request: one `aws s3 cp` per added or changed file and one `aws s3 rm` per removed one, as argument lists and never through a shell. The volume is the source of truth and the mirror is one way. The paths the bucket has not confirmed wait in a journal on the volume, under one 120 second deadline for the whole mirror, so a failing bucket delays the mirror and never a request. At start, before the first poll and only onto a missing or empty memory directory, the runner downloads the prefix into a staging directory, holds it to the same bounds, and moves it into place with one rename, up to 10 minutes; a restore that fails is retried before each request with a growing wait, and while one is pending nothing is put into the bucket or deleted from it. The task role needs `s3:ListBucket` limited to the prefix and `s3:GetObject`, `s3:PutObject` and `s3:DeleteObject` on objects under it, plus `kms:Decrypt` and `kms:GenerateDataKey` for a customer-managed key; turn on versioning. The image carries the AWS CLI, and the entrypoint refuses to start on a plain machine that names a bucket and has no `aws`.

An operator can now run a test job from the Integrations card. The platform queues a job with `"test": true` through the same queue; the runner runs no fix, opens no pull request and pushes nothing, and reports `not_validated`, one sentence and six steps: `collected` (the brief was fetched), `cloned` (the first repository set to the self-hosted runner, or a scratch directory when none is), `model` (one line asked of the model through `opencode run --agent sre-fix` as the agent's account, with the fix path's scrubbed environment and at most two minutes), `memory` (a marker written to the memory directory and removed), `bucket` (a marker put under the memory prefix and removed again, judged on those two calls alone) and `reported`. The first step that fails is reported with its sentence of at most 300 characters and the later ones as not run. The report gains an optional `test` object for it.

An operator can now decide what the agent holds. The agent runs as a second account (`agent`, uid 10002 in the image; `sre-agent-fix-agent` on a host), holds no capability and no supplementary group, and cannot read the runner's environment, the memory directory, the git directories or another repository's clone. Its work tree is a real git repository made from a bundle of the base commit's history, so `log`, `blame`, `diff`, `bisect` and local commits work, and the pull request is still the difference between the work tree and the real base, computed and committed by the runner. It gets none of the runner's AWS variables unless `SRE_AGENT_AWS_ACCESS=1`, and its `GH_TOKEN` is the runner's repository token, or the one in `SRE_AGENT_GITHUB_TOKEN` when that is set, which can be a fine-grained token with Contents read-only so the agent can clone and read but not push. The runner's own token is on no command line: its `git` calls that talk to GitHub read it from their environment through a credential helper for github.com alone, so another account cannot read it from `/proc/<pid>/cmdline`, and `gh` gets it as `GH_TOKEN`. The agent's home is one per repository and belongs to the agent only for the length of that repository's run; before every run the runner removes from it everything opencode loads by itself (`.config/opencode`, `.opencode`, `.claude`, `.claude.json`, `.agents`: configuration, plugins, agent definitions, instructions, skills) and sets `OPENCODE_DISABLE_CLAUDE_CODE`, `OPENCODE_DISABLE_CLAUDE_CODE_PROMPT`, `OPENCODE_DISABLE_CLAUDE_CODE_SKILLS`, `OPENCODE_DISABLE_EXTERNAL_SKILLS` and `OPENCODE_PURE`, because a plugin a hostile run planted there would run before any gate in every later run; the test suite proves it against the pinned opencode. A process of the agent's account that outlives every attempt to end it is named in the report, and nothing is published for that request. `SRE_RUNNER_SETUP` names an executable file in the container that the entrypoint runs once as root before the first poll, with an allowlisted environment, for system packages the image lacks; the entrypoint refuses a URL, a relative path, a script on the workspace or under `/tmp`, `/var/tmp`, `/dev/shm`, `/run/lock` or `/var/lock`, and a script whose path, as given or as resolved, has a directory above it, or is itself, writable by every account. The image gains `build-essential`, `make`, `python3` with `pip` and `venv`, `util-linux`, `xz-utils` and `mise`. The runner trims the whitespace around the poll key, both repository tokens and the provider keys, and refuses to start when one has a line break inside it.

What a customer must change on upgrade:

Each repository is cloned again once. A clone from the earlier layout (`<owner>/<repo>` at the top of the workspace) is moved under `repos/` when the runner starts and is cloned again into the new layout on its next request, with its git directory in `gitdirs/`, because nothing inside a `.git` that an earlier release's agent could write is trusted. The agent's homes are created on the volume, one per repository.

A bucket's first sync. When `SRE_MEMORY_BUCKET` is set and the volume already holds memory (an upgrade, a bucket added later, or the bucket or the prefix changed), every file that passes the bounds is journaled and uploaded once, under the mirror's 120 second deadline and over as many requests as it takes; it only uploads and deletes nothing in the bucket. Into an empty volume and a bucket that holds memory, the restore runs first.

Two accounts, and what the image needs. The container starts as root, and only the container does, so the runner can start every agent run as the second account and hand it one checkout at a time. It needs six capabilities and no others, `SETUID`, `SETGID`, `CHOWN`, `DAC_OVERRIDE`, `FOWNER` and `KILL`, all six of which are in Docker's default set (which holds fourteen); a deployment that drops capabilities must add those back to get the split. One that is not root and lacks them still starts: the runner runs the agent as its own account, as releases before v1.5.0 did, with a `warn` line at start naming the missing capabilities and an `agent_isolation` entry in the evidence of every report, so the minor release on the moving `:v1` tag does not take down a deployment that follows the manifest of an earlier release. A start that is root and lacks any of the six never falls back, because the one account there is root: the runner refuses to start, names what is missing and says the agent would run as root. A host directory mounted at `/workspace` can have any owner, because the runner sets it when it starts. A kubeconfig or token file the agent should read has to be readable by uid 10002. The agent no longer receives AWS credentials from the runner's environment, which it did before: set `SRE_AGENT_AWS_ACCESS=1` to keep that, knowing it gives the agent everything the role holds. That removes the runner's variables, not a role the machine provides itself (an instance profile reached through the metadata service, an IRSA or Pod Identity token file): any account on the machine reaches those unless you close them, and the README says how. It now holds a repository token as `GH_TOKEN`, which it did not before. Anything built on `FROM ghcr.io/segfaultpw/sre-agent-opencode-runner` should leave `USER` and `ENTRYPOINT` alone.

Kubernetes. The manifest of an earlier release (`runAsNonRoot`, `runAsUser: 10001`, `fsGroup: 10001`, every capability dropped) still starts on `:v1` and works as v1.4.0 did, in one account, saying so; to get the split, replace the pod's `securityContext` (`runAsNonRoot` and `fsGroup` are gone) with `runAsUser: 0`, `allowPrivilegeEscalation: false`, and `capabilities` that drop `ALL` and add the six above. Give the workspace a PersistentVolumeClaim instead of an `emptyDir` to keep what the runner now keeps; the README has the whole manifest.

systemd. Run `sudo bash runner/install-runner.sh` again from a clone of this release. It checks that `setpriv` (util-linux) is installed, creates the `sre-agent-fix-agent` account, sets the state, workspace and agent-home directories to mode 0711 instead of 0750, and installs a unit that sets `SRE_AGENT_USER`, holds the six capabilities as ambient capabilities with a bounding set of the same six, and still never runs as root. The runner's own `git`, `gh` and `aws` calls now run with `HOME` set to `/var/lib/sre-agent-fix-runner/runner-home`, a directory of its own that the runner makes (mode 0700), and no longer with the account's old home, `/var/lib/sre-agent-fix-runner`: in releases before v1.5.0 the agent ran as that same account and could write an AWS CLI configuration with a `credential_process`, or a `gh` configuration, there, which the runner's own calls would then have read with its credentials. Nothing is moved or deleted in the old home; the runner just stops reading it. A plain machine that names a bucket needs the AWS CLI on its PATH.

Platform versions. A platform older than the release that reads `memory` and `test` ignores both keys, so reports arrive complete without the memory list and the steps. The test job needs the platform's button: a runner older than v1.5.0 that is handed one reads it as an ordinary request without a repository and answers with a diagnosis, and the card says the runner needs updating.

## v1.4.0

Pull requests follow Conventional Commits. A repository that checks its titles (a required job, a squash merge convention, a release tool reading commit types) refused what this package opened: the CI door retitled every pull request `ABC-12: <title>`, and the machine door used the first sentence of the agent's final message cut to 72 characters, with `SRE Agent fix <handoff id>` when there was none. SRE Agent's own agent already titled its pull requests `type(scope): subject`; both doors here now apply the same rules.

The rules, in order: every U+FEFF is removed; leading `[tags]` are dropped, and so is the key of the card the request came from followed by a colon or whitespace, in any order (no other key is a prefix, so `SHA-256: verify`, `GPT-4 support` and another card's `OPS-7: widen` keep their subjects); the first line that is not blank is the text; a title that already is `type(scope)!: subject` with one of `feat`, `fix`, `chore`, `docs`, `refactor`, `perf`, `test`, `build`, `ci`, `style` or `revert` is kept with its type in lower case; anything else becomes `fix: <text>`; a header with no subject, or with one made only of combining marks (the combining diacritical blocks, the variation selectors and the zero width joiner, listed by block because each engine reads `\p{M}` from the Unicode version it ships), takes `apply the requested fix`; the result is one line of at most 256 characters, a scope that would leave fewer than ten characters for the subject is dropped rather than cut in half, and a cut that leaves no subject takes the fallback subject. A type is judged against the list in ASCII, because a regular expression that folds case also folds U+017F (long s) onto `s` and would let `docſ:` through, and the card key is matched in ASCII for the same reason. Whitespace is a space or a tab and a line break is LF, CR, VT, FF, U+0085, U+2028 or U+2029: jq's Oniguruma, Node and SRE Agent's PCRE each draw their own Unicode whitespace class (Node takes U+FEFF for whitespace and U+0085 for none), so none of them is used.

The CI door applies them in the marking step, through `scripts/conventional_title.sh`, a jq filter, because the workflow already depends on jq and runs on a runner this package does not control. The machine door applies them in `runner/conventional_title.js` to the first line of the agent's final message, and that one line is both the commit message and the pull request title; with nothing usable the title is `fix: apply the requested fix (<handoff id>)`. The two implementations are run over one table of cases, `tests/fixture/conventional_titles.json`, and over 300 generated inputs compared between them, so a rule changed in one and not the other fails the tests; SRE Agent's own test suite runs a byte for byte copy of the table. The CI door passes the card key it read from the tracking issue; the machine door is handed none, so it drops no key. The Node module and SRE Agent cut a title on a grapheme boundary; the jq filter cuts on a code point and backs off a mark of any script, a joiner, a skin tone and a pictograph joined to the one before, which gave the same title as the other two for each of 6000 generated inputs, under jq 1.6 and 1.8. The filter uses only builtins of jq 1.6, which is what an `ubuntu-22.04` runner carries.

The card key moves to the body. The marking step now writes `Refs: ABC-12` on a line of its own beside the marker line and the version stamp, through `scripts/pr_body.sh`, and reads the key from the tracking issue through `scripts/card_key.sh`: the `Refs: KEY` line directly before the marker line at the end of its body, which is the block SRE Agent appends after everything a card, a requester or a model wrote, and otherwise `KEY:` at the start of its title, which is where an SRE Agent before this change put it. A `Refs:` line anywhere else in the issue body is somebody's words and names no card. SRE Agent adopts a pull request by the marker, which this package always writes, and a title that starts with the key still adopts the pull requests of v1.3.0 and earlier. An SRE Agent release that writes the `Refs:` line into the tracking issue also adopts a pull request by that line when the marker was lost; an older one adopts by the marker alone and ignores the line. The marker line and the version stamp are untouched, byte for byte, and nothing is appended twice.

What a customer must change: nothing. A workflow pinned to `@v1` takes the change with the next run, a frozen pin moves when it is bumped, and the runner image and the systemd install move with their own upgrade. A repository that depended on the card key leading the title (a search, a dashboard, a branch protection rule) should read the `Refs:` line in the body instead.

## v1.3.0

SRE Agent's own `/opencode` comment starts a run again. The opencode action asks GitHub for the commenting user's collaborator permission on every run a user event starts, in App mode and in token mode alike, and a GitHub App holds no permission level on a repository: the platform's comment answered `none`, and every run it started failed with "User sreagent-app[bot] does not have write permissions" before the agent read anything. No input and no environment variable skips that check, and upstream skips it only for the two repository events, `schedule` and `workflow_dispatch`. A customer reported it as issue #1; their own workaround was to filter the bot login out of the workflow's condition, which leaves the platform with no door at all.

So the example workflow relays. A comment from the login in `vars.SRE_AGENT_BOT_LOGIN` reaches a `relay` job whose `permissions` block is `actions: write` and nothing else, and whose one step fires a `workflow_dispatch` of the same file carrying the issue number and the relaying comment's id. GitHub's rule that an event created with `GITHUB_TOKEN` starts no further workflow has two exceptions, and `workflow_dispatch` is one of them, which is what makes a relay work at all; the run it starts has no commenting user, so there is nothing for the action to check. That permission is the smallest one that starts a run rather than a small one, since a token holding it can start any `workflow_dispatch` workflow in the repository and cancel or re-run runs; what keeps the relay to one thing is its single fixed step. A member's own comment still runs the fix job directly and on the same terms as before, and that job now refuses the relay's login instead of admitting it, so a `SRE_AGENT_BOT_LOGIN` that names a person by mistake starts one run and not two. The fix job also accepts any `workflow_dispatch` of the workflow, which anyone with write access to the repository can fire from the Actions tab with an issue number of their choosing: the same trust the comment door already places in a collaborator.

The reusable workflow takes `issue_number` and `comment_id`, and resolves the issue once. A dispatched run's event carries no issue, so the diff gate, the marking step, the decline step and the token-mode diagnostic all read one job-level value that prefers the input and falls back to the event, and the concurrency group, which cannot read the environment, repeats the same expression, so a comment and a dispatch for one issue still cannot run at once. The brief is the issue's own body, read by a step that runs on the dispatched door alone and handed to the action as its prompt, which is mandatory there because there is no comment to read; the issue's title and body reach the marking and decline steps the same way, and that is how the card key and the marker line still reach the pull request. The body travels between steps behind a delimiter drawn from `/dev/urandom`, because it is text an attacker can write.

Finding the run's own pull request knows both branch namings. The action names a comment-started run's branch `opencode/issue<N>-<timestamp>` and a dispatched one `opencode/dispatch-<hex>-<timestamp>`, and the second carries no issue number, so two dispatched runs of one repository each see the other's branch. `run_prs.sh` reports every candidate with a `mine` field, true when the body carries the link to this run that the action writes as its footer, and the two callers read it differently. The marking step keeps only this run's own, because marking another run's would put this run's card key and marker line on it and the platform would adopt the wrong one, and it warns when candidates existed and none of them linked this run, which is what a change to that footer would look like. The diff gate inspects and closes every candidate, because a pull request that touched a protected path has to be closed whichever run opened it, and fails the job only on this run's own: failing on another run's would leave this run's own work unmarked and have the platform record a request that succeeded as failed.

A dispatched run cannot answer on the issue the way the action does, so the workflow answers for it. The action reacts to no comment and posts nothing there for a run a comment did not start, so the reusable workflow sends the rocket reaction itself with the token it already holds, and when such a run opens no pull request it writes the decline itself: a comment beginning `Declined:` with the issue's marker line already in it, so SRE Agent ends the request that asked rather than the newest one on the issue. The marker has to be there as the comment is posted, because SRE Agent reads a decline off the comment it was sent and skips every edited delivery; the version stamp is appended after, along with the marker on the comment door, where the action writes the comment and no step of the workflow composes it. What the comment cannot carry is the agent's own words, because the action exposes them nowhere but the run's log, so its reason reads the same every time and links the run. A relayed run that saw pull requests on dispatch branches and could not recognise one of them as its own posts no decline at all, since one of them may be this run's work under a footer the action has changed, and the platform's own sweep ends the request instead. A member's own comment is unaffected and still gets the action's own answer. An allowance for a GitHub App in the action's own check would let the relay go and the words come back, which is asked upstream rather than worked around here.

What a customer must change: re-copy `examples/opencode.yml`, or re-run `scripts/install.sh`, and put `model` and `provider_key` back. Anyone who worked around the failure by filtering `SRE_AGENT_BOT_LOGIN` out of the workflow's `if:` should drop that filter, since the relay job is where that login is admitted now. The new file has to reach the default branch: GitHub registers `workflow_dispatch` from the default branch's copy, and the relay names `.github/workflows/opencode.yml`, the path the install writes.

## v1.2.0

A runner answers fix requests on a machine the customer owns. `runner/runner.js` holds an outbound long poll against `GET /api/fix-runner/queue`, authenticated by an organization API key whose only scope is `fix_runner:poll`; it fetches the brief with the token the queue hands it, checks the repository out on a `sre-agent/<handoff id>` branch or runs with no checkout when the request named none, runs `opencode run --agent sre-fix` once with the brief on stdin and this package's configuration in the environment, stages what the agent left, runs `scripts/protected_paths.sh` over it, pushes, opens a draft pull request carrying the marker line and the version stamp, and reports the answer. It is a single Node file with nothing but the standard library behind it, because it is installed on somebody else's machine. It is also the only thing there that touches git or the network, so the agent keeps every `git push`, `curl`, `wget` and `webfetch` deny it has in CI, and a request that resolved no repository, which no CI door can take, is answered with a diagnosis.

A container image, `ghcr.io/segfaultpw/sre-agent-opencode-runner`, built for amd64 and arm64 on a runner of each architecture and published on every release with a frozen `vX.Y.Z` tag and a moving `v1`. It carries node, git, `gh`, opencode, kubectl and the AWS CLI, and the package's own VERSION, configuration, agent and scripts, root-owned and not writable by the unprivileged account the agent runs as. opencode is pinned by version and by sha256 for each architecture, because that binary is what enforces the fences, and the x64 build is taken in its baseline form since the installer's AVX2 check would read the build machine's processor rather than the customer's. The image is built in CI on every push as well, so a Dockerfile is never first exercised at release time.

A systemd install for a plain machine. `runner/install-runner.sh` checks every prerequisite before the first write and names the command that closes each gap, then creates the account and the directories, copies the package to `/opt/sre-agent-opencode` root-owned, installs `sre-agent-fix-runner.service`, and writes `/etc/sre-agent-fix-runner/env` as a 0600 template with no values in it, since the credentials are the operator's to paste. The unit runs the same entrypoint the image runs, so a container and a plain machine refuse to start for the same reasons and in the same words, and it holds one writable path, so a run cannot edit the fences the next run will load.

The README gains "Run it on your own machine": what the door is and how it differs from the CI one, the API key and its single scope, the three installs, registering the runner, the environment variables, what happens on a fix request end to end, what happens while the runner is down, the costs, and what actually bounds the agent, which is the role the machine holds rather than the list of denied commands.

The repository being fixed can no longer override the fences or replace the agent. opencode merges what the package passes in through `OPENCODE_CONFIG_CONTENT` with the repository's own configuration rather than replacing it, and that merge keeps the repository's key order while a permission resolves to the last matching rule, so a tracked `opencode.json` naming the same keys held the package's denies at its own indexes and let its own catch-all win: against opencode 1.18.25, `kubectl delete pod p` resolved to allow with such a file in the checkout. What the loader reads out of `.opencode/` is worse. A file under `.opencode/plugin` is imported and ran before any gate was consulted, and so is one under `.opencode/plugins`; `.opencode/agents` is read and so is `.opencode/agent`, where a definition of the repository's own replaced this package's prompt and every permission in it.

Both doors now run `scripts/strip_repo_config.sh` over the checkout before opencode starts, and it removes the WHOLE `.opencode` directory along with `opencode.json*` at the root; the door then writes the package's own agent into the emptied tree. Not a list of names: the list was wrong twice, the next opencode release can add a path without telling anyone, and an empty directory covers `.opencode/commands`, `.opencode/skills`, `.opencode/tools` and whatever comes next by construction. A tracked path is marked `skip-worktree` first, so no pull request carries its removal, and a repository that tracks its own `.opencode/agents/sre-fix.md` is no longer refused, because it no longer collides with anything. `OPENCODE_DISABLE_PROJECT_CONFIG` closes neither path, which is why this is a script and not an environment variable.

`gh` is refused, and on the CI door that was a privilege escalation rather than a convenience: the workflow puts `GITHUB_TOKEN` in the agent's environment, so `gh pr merge` and `gh api -X PUT` went around the `git push` deny and the protected paths gate at once, and the agent could have merged its own pull request. It is written as one pattern per way of invoking it rather than one for the two letters: bare, single or double quoted, by path, behind an environment prefix, through `env`, plus `gh api` and `gh pr` wherever they appear and the three ways a shell is asked where the binary is. Matching the letters alone refuses `grep gh file` and a commit message mentioning gh, which the agent has every reason to type while running your build; matching too little let a single quote in front of it walk past. What remains is the class the fences already name: an interpreter chain that resolves the binary another way and uses a different subcommand. On the runner door this is the second line, because the runner deletes `GH_TOKEN` and `GITHUB_TOKEN` from the environment it starts the agent in. `rm` with its flags transposed, split, spelled out or capitalised (`rm -r -f`, `rm --recursive --force`, `rm -fR`) is refused with `rm -rf`.

The eight denies the package started with are prefix-immune too. `curl x` was refused while `HTTPS_PROXY=y curl x`, `env curl x` and `/usr/bin/curl x` were allowed, and `git push origin HEAD` was refused while `git -C /tmp/r push origin HEAD` was allowed; those two are what the claim that only the workflow or the runner touches git and the network rests on. Each is restated in the shape the cloud and cluster families already use, `rm -fr` joins `rm -rf`, and each is probed bare, behind an environment prefix, behind `env`, by absolute path, and for git with the flag between the binary and the verb.

The bash gate refuses the mutating cloud and cluster commands as well: the `kubectl` write verbs (`delete`, `apply`, `create`, `replace`, `edit`, `patch`, `scale`, `exec`, `cordon`, `drain`, `label`, `annotate`, `expose`, `run`, `debug`, `taint`, `cp`, `attach`, `port-forward`, `proxy`, `certificate approve`, `rollout restart`, `undo`, `pause`, `resume`, and `set` by subcommand); `helm upgrade`, `install`, `uninstall` and `rollback`; `terraform apply`, `destroy`, `import`, and `state rm`, `mv`, `push` and `replace-provider`; the AWS CLI's 37 mutating verb families, written as `*aws *<verb>-*` so a service the CLI adds later is covered without a new rule; the writing `aws s3` verbs; `aws configure set`, `aws ssm start-session` and `aws ecs execute-command`; and the mutating calls whose verb carries no hyphen, such as `lambda invoke`, `sns publish` and `cloudformation deploy`. Every pattern tolerates flags before the verb and an environment prefix in front of the command, which is how these are typed in practice; an anchored pattern alone allowed `kubectl -n prod delete pod x`.

opencode parses a command line and asks about each command in it, denying the call when any one of them is denied, so a refused command is not admitted by being chained after an allowed one. What a pattern sees is that command as written, arguments included, which is why the reads needed care: a verb written as a bare substring took `kubectl get volumeattachments`, `kubectl logs deploy/kube-proxy` and `terraform state list` with it. The mutating subcommand is named wherever a family also holds reads, and the read verbs are allowed again after the deny block: `kubectl get`, `describe`, `logs`, `top`, `explain`, `api-resources`, `auth can-i`, `version` and `cluster-info`; `terraform plan`, `show`, `output`, `validate`, `state list`, `state show` and `state pull`; and four AWS reads whose data has no other read path, `aws logs start-query` and `stop-query` and `aws cloudtrail start-query` and `cancel-query`, since a Logs Insights query is the only aggregating read of a log group and a Lake query the only read of an event data store. Every re-allow is anchored at its verb, because a command carrying a substitution is judged by its whole text and a re-allow with a wildcard in front of the verb can be reached from inside one; the cost is that the same read behind an inline credential prefix stays denied, and on a runner the credentials come from the process environment or the machine's role rather than from a prefix. A read whose own verb is a mutating word, such as `aws logs start-live-tail`, and a read whose arguments carry one are still refused. Over-denial is the safe direction for a deny rule.

The list is a speed bump and not a boundary: an interpreter such as `sh -c` or `python -c`, or a script the agent writes and then runs, is a single command whose contents no pattern here describes. It stops a careless step. What holds is the role granted to the machine the agent runs on.

One agent prompt now serves both doors. It no longer says it is running inside a repository's own CI, because a runner started on a machine you own runs the same agent under the same fences, and two copies of the prompt would drift. It also gains a step for a request that resolved no repository: investigate with the read-only commands available, answer with a diagnosis, the evidence for it and the repository the change probably belongs in, and change nothing.

The prompt's untargeted step says what it keeps of the pull request contract: the version stamp, so the answer says which version produced it, and not the marker line, which has no card to tie an answer to when there is no pull request.

The runner never reports `validated_fixed`. An opened pull request is reported as `not_validated` carrying its URL, and the summary says the change is an unmerged draft that nothing has verified in a running system. The runner cannot deploy, so it cannot validate; the platform quotes the outcome onto the card, where "validated fixed" would have read as a claim that the problem was solved.

The runner's own credentials are removed from the agent's environment: the poll key, the repository token, `GH_TOKEN` and `GITHUB_TOKEN`. The provider key stays, since opencode needs it to call the model. All three of the runner's credentials are redacted from every log line and every report, including the ones a failing `git` or `gh` prints itself.

The agent's own final message is redacted the way every other line is. It becomes the report's summary, the card comment and the pull request body, and it was the one path the runner's poll key, repository token and handoff token could have travelled on. Four claims in the README are narrowed to what the code keeps: a runner that dies between its push and the pull request leaves a branch behind, the shell is where "the agent cannot reach the network" stops holding, the draft state is a convenience rather than a control, and the redaction set is those three credentials and not the provider key, which the runner never learns the variable name of.

A runner an operator switches off in SRE Agent waits instead of exiting. The queue refuses it with 403 and a stable `runner_disabled` code, which the runner treated as a refused key: it exited naming `SRE_API_KEY`, and under `Restart=always` that is a restart loop into `failed` while the customer is told to check a credential that is fine. It now says the runner is switched off, says the key is not the problem, and polls once a minute until it is switched back on. Every other 401 and 403 is still fatal.

A run the runner cannot fully kill is still reported. The child's `close` event needs the process gone and every pipe closed, and a grandchild that put itself in another session survives the group kill while holding them, so the promise never settled and no report was sent at all: the platform then waited out its 45 minute sweep and told the customer their runner never answered, while it was sitting there alive. The kill now answers on its own after a short grace, lets go of the pipes, and the report says a process may still be running on the machine.

A queue answering more than one request is worked one request per poll. The platform's sweep bound runs from dispatch on every job it hands over, so a batch worked in series spent the second job's bound on the first: it would be swept mid-run, its report refused, and its pull request left in the repository with nothing pointing at it. The rest stay in the queue and the next poll returns them, which costs one round trip and loses nothing, since a request is only taken when its brief is fetched.

The systemd installer upgrades without destroying what is installed, and says when it cannot. The package tree is assembled beside the target and swapped in, rather than each directory being deleted and then copied, so a copy that dies on a full disk or a bad clone leaves the working install running instead of a package missing half its files. An upgrade now restarts a runner that was already running, which is the difference between a customer's logs agreeing with them and not. `--prefix` with nothing after it exits 2 saying which argument was wrong, rather than exiting 1 in silence.

An install that would produce a service that cannot start is refused. The unit sets `ProtectHome=yes`, so a `node`, `git`, `gh` or `opencode` inside a home directory is on the operator's PATH and invisible to the service, and opencode's own installer writes to `~/.opencode/bin`. The installer now refuses while one of the four is there and prints the copy that puts it on the system PATH, and the README's install steps carry that copy.

Two builds of one runner image are the same binaries. The image stamps its own version into every pull request body it opens, so it was claiming a reproducibility it did not have: the base image floated under `node:22-bookworm-slim`, and the AWS CLI was fetched with no checksum. The base is pinned by its multi-architecture digest, the AWS CLI by content like opencode, kubectl and gh already were, `bash` is installed by name rather than inherited, and `OPENCODE_DISABLE_AUTOUPDATE=1` is set for the whole image rather than only for the agent's own process, so nothing in it can replace the binary that enforces the fences. The apt packages stay unpinned on purpose, and the Dockerfile says why: Debian's mirror serves only the current point release, so an exact version would trade a reproducible image for one that stops building the day a security update lands.

The pins in the runner image go stale on purpose, and a bump is a release of this package like any other. The base image is pinned by its multi-architecture digest and the AWS CLI by the sha256 of the artifact the image was built against, alongside the opencode, kubectl and gh versions that were already pinned; each is recorded here when it moves, so pulling a newer image is the whole upgrade and nothing changes underneath a running one.

## v1.1.0

A run that declines now marks its comment. When the action opened no pull request and left a comment beginning `Declined:` on the tracking issue, the workflow appends the issue's marker line and the version stamp to that comment, as it already does to a pull request body. SRE Agent ends the remediation the marker names; a decline without one fell back to the most recently dispatched request, which is the wrong one when a request was superseded while the run was going. An issue body carrying no marker leaves the comment as the action wrote it.

`scripts/install.sh` installs the caller workflow across an organization. It reports every prerequisite once with the command that closes it, and refuses before the first write when one is missing: the token's `workflow` scope, the opencode App installation or the Actions pull request policy, the provider secret, and the `SRE_AGENT_BOT_LOGIN` variable. `--dry-run` writes nothing.
